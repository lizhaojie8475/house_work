计划一：家务管家小程序的算法内核与云函数后端。前端页面与发布流程属于计划二，不在本 PR 范围。

## 做了什么

- **共享纯逻辑**（`shared/`）：本地日历日换算、浮动与固定两种周期的到期日计算、紧急度分档与首屏排序、云数据库访问层。均不依赖微信 API，依赖通过参数注入。
- **`api` 云函数**：单入口 + action 路由，18 个 action 覆盖家庭（创建/邀请加入/成员/设置）、家务（增删改查/批量导入/归档）、完成流水（打卡/补录/撤销/跳过/历史）、成员（资料/订阅额度/个人信息）。
- **`reminder` 云函数**：每小时触发，按家庭聚合成一条订阅消息推送。
- **模板库**：39 条常见家务带推荐周期，覆盖六个分区。
- **测试**：300 个，18 个套件，覆盖周期计算边界（跨月、闰年、月末溢出、固定周期跳过不累积）、鉴权、并发与失败路径。

## 两个决定整体架构的约束

**鉴权不能放在数据库。** 云开发的安全规则只能表达「仅创建者可读写」这类以身份为主体的条件，无法表达「同一家庭的成员可互相读写」——那需要关联查询。所以集合设为仅管理端可读写，全部读写经云函数代理，身份取自 `cloud.getWXContext().OPENID`（微信侧注入，客户端无法伪造）。`requireMember` / `requireOwner` 就是整套访问控制。

**推送额度是用户逐次授权攒出来的稀缺资源。** 微信只允许「一次性订阅消息」，每次授权换一条推送权限且无服务端接口可查余额。所以提醒任务把一个家庭的待办聚合成**一条**消息而不是每件家务一条，并且任何误扣或误清零都是不可挽回的用户损失。

## 审查中修掉的几个真实缺陷

- `router` 对 `actions[action]` 和 `CODES[err.code]` 未做自有属性检查：客户端传 `action: "toString"` 能调到原型链上的函数，传 `code: "constructor"` 能让内部错误消息伪装成业务错误泄露。
- `createOrGet` 对已退出家庭的成员会再插一条同 openid 记录，导致该用户永久被锁在门外。
- `chore.update` 原本每次都重算到期日：改个家务名字就会把从未完成过的家务的到期日悄悄重置成「今天 + 周期」。现在只在周期配置变化时重算。
- 用户填的「上次做是什么时候」被验证后丢弃、从未持久化，撤销一次完成就会永久丢失。
- `subscribeQuota` 的读-改-写跨越网络调用；200 上限用相对增量纠正时自身会竞争（195 并发两笔 +20 会跌到 165）。现已改为原子 `inc` 加带条件的绝对写。
- 四个列表查询用固定 `.limit()` 会静默截断，其中 `listFamiliesByReminderHour` 会让超出上限的家庭永久收不到提醒且无任何报错。
- 跨家庭家务 id 访问原本返回 `FORBIDDEN`、不存在返回 `NOT_FOUND`，构成 id 存在性探测器。现已统一为同码同文案。

## 合并后仍需人工完成

见 `docs/setup-notes.md`：注册个人主体小程序、选服务类目、开通云开发、申请订阅消息模板并对齐 `message.js` 中的占位字段名、建立集合与索引（含三个唯一索引，`reminder_sends` 的唯一索引是提醒去重的正确性前提）、上传云函数并在云控制台联调。

`shared/repo.js` 的查询语句没有可运行测试覆盖（契约测试只比方法集，不执行查询），`docs/setup-notes.md` 列出了必须在云控制台人工验证的清单。
