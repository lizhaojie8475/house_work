# 家务管家小程序 · 第一期设计文档

- 日期：2026-09-17
- 状态：已确认，待编写实现计划
- 范围：第一期（可独立上线自用的完整产品）

## 1. 背景与目标

家里有一批周期性家务（洗衣机自清洁、刷马桶、换床单、洗油烟机、清洗扫地机器人、浇花、擦玻璃等），它们的共同特点是间隔长、容易忘、忘了又说不清上次是什么时候做的。

本项目做一个微信小程序，解决三件事：

1. 记录每件家务的完成历史，随时能回答「上次是什么时候做的」
2. 根据周期算出下次该做的日期，并按紧急度排序，打开就知道今天该干什么
3. 临近到期时通过微信订阅消息主动提醒

使用场景是**家庭共享**：家里多人看同一份家务清单，谁做的记在谁名下。

### 成功标准

- 家庭成员能通过分享链接加入同一个家庭，看到同一份清单
- 存量家务可以在 5 分钟内从模板库批量导入并填好上次完成日
- 首屏第一眼就能看出最该做的是哪件，完成只需点一下
- 到期前能收到微信推送，且推送额度在正常使用下不会频繁断供
- 小程序通过微信审核并正式发布

## 2. 范围

### 第一期包含

- 家庭空间：创建家庭、生成邀请码、分享卡片邀请成员、成员列表
- 家务管理：增删改查、归档，含房间分组、预估耗时、SOP 备忘三个描述性字段
- 两种周期：浮动周期（完成后 N 天）与固定日历（每周/每月/每年某日）
- 完成打卡：一键完成、补录历史日期、撤销最近一次完成、跳过本次
- 待办首屏：按紧急度四档分组排序
- 模板库：30+ 条常见家务带推荐周期，首次进入引导批量创建
- 历史时间线：每件家务的完成流水，显示时间与完成人
- 订阅消息提醒：每日定时扫描、按家庭聚合成一条推送、额度管理与续订引导

### 明确不做（第一期非目标）

以下功能已与用户确认推迟，但数据模型需预留扩展位：

- 第二期：负责人与自动轮值、贡献榜与统计看板、微信分享催办、智能周期建议、「15 分钟能干啥」推荐
- 第三期：耗材库存管理、拍照记录
- 永久不做：家务积分/奖励体系（用户已明确排除）
- 一个用户同时属于多个家庭。第一期假设一人一个家庭；`members` 独立成集合而非内嵌数组，为将来放开这一限制留出空间

## 3. 技术选型

| 层次 | 选择 | 理由 |
|---|---|---|
| 前端 | 原生微信小程序 | 无框架抽象层，调试路径最短 |
| UI 组件 | TDesign MiniProgram | 腾讯官方，视觉与微信原生一致 |
| 后端 | 微信云开发云函数（Node.js 18） | 免服务器、免域名、免 ICP 备案 |
| 数据库 | 云开发云数据库 | 与云函数同生态，免运维 |
| 定时任务 | 云函数定时触发器 | 承载每日提醒扫描 |
| 单元测试 | Jest | 覆盖周期计算纯函数 |

选择云开发的决定性理由是它消除了「能否发布上线」这个最大不确定性——没有 ICP 备案环节（大陆备案需 2–3 周），写完即可提审。代价是绑定微信生态，但周期计算与业务规则都写成与云开发 API 无关的纯函数，将来迁移到 HTTP 后端时只需替换入口层。

家庭级用量完全落在云开发免费额度内。

## 4. 数据模型

五个集合。所有集合的数据库权限均设为「仅管理端可读写」，详见第 6 节。

| `createdAt` | number | 创建时间戳 |

| `nickname` | string | 昵称，用户主动填写或授权获取 |
| `avatarUrl` | string | 头像 |
| `role` | string | `owner` / `member` |
| `subscribeQuota` | number | 剩余订阅消息推送额度 |
| `joinedAt` | number | 加入时间戳 |
| `active` | boolean | 是否在家庭中，退出时置 false 而非删除，保留历史记录归属 |

### 4.3 `chores`

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 家务 ID |
| `familyId` | string | 所属家庭 |
| `name` | string | 家务名称 |
| `icon` | string | emoji 或 TDesign 图标名 |
| `room` | string | 房间/分区，自由文本，模板库提供预置值 |
| `scheduleType` | string | `floating` / `fixed` |
| `intervalDays` | number | 浮动周期天数，仅 `floating` 使用 |
| `fixedRule` | object | 固定日历规则，仅 `fixed` 使用，见 4.3.1 |
| `estimatedMinutes` | number | 预估耗时（分钟） |
| `notes` | string | SOP 备忘，如「用筒自洁模式，投 1 包清洁剂」 |
| `reminderLeadDays` | number | 提前几天开始推送提醒 |
| `lastDoneAt` | number \| null | 上次完成时间戳，冗余字段 |
| `lastDoneBy` | string \| null | 上次完成人 openid，冗余字段 |
| `nextDueAt` | string | 下次到期的本地日历日，格式 `YYYY-MM-DD`，冗余字段 |
| `archived` | boolean | 是否归档 |
| `createdAt` | number | 创建时间戳 |
| `createdBy` | string | 创建人 openid |

`lastDoneAt`、`lastDoneBy`、`nextDueAt` 是从 `chore_logs` 派生的冗余字段，目的是让待办首屏能直接按 `nextDueAt` 排序，无需每次进入都做聚合计算。它们只由云函数在写入流水时同步更新，是单一写入路径。

#### 4.3.1 `fixedRule` 结构

```js
// 每周（支持多选，如每周二、四）
{ type: 'weekly', weekdays: [2, 4] }   // 0 = 周日

// 每月某日，月末溢出取该月最后一天（如 31 号在 2 月取 28/29 号）
{ type: 'monthly', dayOfMonth: 1 }

// 每年某月某日
{ type: 'yearly', month: 4, dayOfMonth: 15 }
```

| `doneAt` | number | 完成时间戳，补录时为过去时间 |
| `doneBy` | string | 完成人 openid |
| `note` | string | 本次备注，可空 |
| `createdAt` | number | 记录写入时间戳，与 `doneAt` 区分以识别补录 |

|---|---|---|
| `_id` | string | 记录 ID |

### 4.6 索引

| 集合 | 索引 |
|---|---|
| `chores` | `(familyId, archived, nextDueAt)` 复合索引，支撑首屏查询 |
| `members` | `openid` 单字段（反查所属家庭）；`(familyId, active)` 复合 |

| `families` | `inviteCode` 单字段 |
| `reminder_sends` | `(openid, dateKey)` 复合唯一，保证当天只发一次 |

## 5. 核心算法

所有日期计算统一在时区 `Asia/Shanghai` 下进行。

### 5.1 时区处理

云函数运行环境默认 UTC。若用时间戳直接判断「今天」，北京时间 00:00–08:00 会被算成前一天，导致提醒整体错一天。

处理方式：`nextDueAt` 只存本地日历日字符串 `YYYY-MM-DD`，比较和排序都是字符串操作，彻底避开时区漂移。云函数内部需要「今天」时，统一调用工具函数把当前时间加 8 小时偏移后取日期部分。只有 `doneAt` / `createdAt` 等「某个瞬间」语义的字段存完整时间戳。

### 5.2 计算 `nextDueAt`

输入：家务的周期配置 + 基准日期（本地日历日字符串）。输出：本地日历日字符串。

**基准日期 `baseDate` 的取值**（两种周期类型通用）：

按优先级依次取 `lastDoneAt` 对应的本地日历日 → 创建时用户填写的「上次完成日」 → 创建当天。

**浮动周期（`floating`）**

```
nextDueAt = baseDate + intervalDays 天
```

语义结果：晚做 5 天，下次整体顺延 5 天，不会累积欠账。

**固定日历（`fixed`）**

```
nextDueAt = 满足 fixedRule 且严格晚于 baseDate 的最近一个日期
```

语义结果：本周日没换床单，下周日照旧到期，不累积成两次。

边界规则：

- `monthly` 的 `dayOfMonth` 超出目标月天数时，取该月最后一天（31 号在 2026 年 2 月取 28 号）
- `yearly` 遇 2 月 29 日而当年非闰年时，取 2 月 28 日
- `weekly` 的 `weekdays` 多选时，取集合中最近的那一天

### 5.3 紧急度分档

设 `d = nextDueAt - 今天`（天数差）：

| 档位 | 条件 | 颜色 |
|---|---|---|
| 已逾期 | `d < 0` | 红 |
| 今天到期 | `d == 0` | 橙 |
| 临近 | `1 <= d <= 3` | 黄 |
| 正常 | `d > 3` | 灰，可折叠 |

UI 着色阈值固定为 3 天，与推送阈值 `reminderLeadDays` 是两个独立概念：前者决定视觉分组，后者决定何时开始消耗推送额度。

**首屏排序**：已逾期（逾期天数多的在前）→ 今天到期 → 临近（日期近的在前）→ 正常（日期近的在前）。逾期最久的排最上面，保证最该做的事永远落在拇指能碰到的位置。

### 5.4 三种写入操作的语义

**完成（`done`）**

1. 写入一条 `chore_logs`，`type = 'done'`，`doneAt` 为传入时间（默认当前，补录时为过去时间）
2. 更新 `chore.lastDoneAt` / `lastDoneBy`
3. 以 `doneAt` 的本地日历日为基准重算 `nextDueAt`

`doneAt` 不允许晚于当前时间。补录一个早于现有 `lastDoneAt` 的日期时，`lastDoneAt` 仍取所有 `done` 流水中的最大值。

**撤销（undo）**

仅允许撤销该家务最近一条 `done` 流水，且调用者必须是同家庭成员。

1. 删除最近一条 `type = 'done'` 的流水
2. `lastDoneAt` / `lastDoneBy` 回滚到上一条 `done` 流水；若已无流水则置 `null`
3. 重算 `nextDueAt`；无流水时基准回退到创建日

**跳过本次（`skip`）**

1. 写入一条 `chore_logs`，`type = 'skip'`
2. **不**更新 `lastDoneAt` / `lastDoneBy`
3. `nextDueAt` 前进一个周期：浮动周期以今天为基准加 `intervalDays`；固定日历取严格晚于当前 `nextDueAt` 的下一个规则日

## 6. 权限与安全模型

云开发数据库安全规则只能表达「仅创建者可读写」这类以 openid 为主体的简单规则，无法表达「同一家庭的成员可互相读写」这种需要关联查询的条件。

因此采取的架构决策是：**小程序端不直连数据库**。

- 所有集合的数据库权限设为「仅管理端可读写」，小程序端任何直接查询都会被拒绝
- 所有读写通过云函数进行
- 云函数通过 `cloud.getWXContext().OPENID` 获取调用者真实 openid，该值由微信侧注入，客户端无法伪造
- 每个涉及家庭数据的 action 入口统一做一次校验：该 openid 在 `members` 中存在、`active` 为 true、且 `familyId` 与请求目标一致

这样成员互见与防越权同时解决，且鉴权逻辑集中在一处。

### 加入家庭的校验

邀请分享卡片携带 `familyId` 与 `inviteCode`。云函数校验：邀请码与该家庭当前 `inviteCode` 一致、未过期、调用者尚未属于任何家庭。校验通过后写入 `members`。家庭所有者可在「我的」页重新生成邀请码，旧码立即失效。

## 7. 云函数设计

两个云函数：

- **`api`**：单一入口，内部按 `action` 字段路由。相比拆成多个细粒度函数，单函数减少冷启动次数、简化部署、方便共享鉴权与工具代码。
- **`reminder`**：定时触发器入口，无对外接口。

### 7.1 `api` 的 action 列表

| action | 说明 |
|---|---|
| `family.createOrGet` | 首次进入时创建家庭或返回已属家庭 |
| `family.join` | 凭邀请码加入家庭 |
| `family.refreshInviteCode` | 重新生成邀请码（仅 owner） |
| `family.listMembers` | 成员列表 |
| `family.updateSettings` | 修改提醒小时、默认提前天数 |
| `member.updateProfile` | 更新昵称头像 |
| `member.addSubscribeQuota` | 用户授权订阅后累加额度 |
| `chore.list` | 家务列表，支持按房间筛选、含归档开关 |
| `chore.get` | 家务详情 |
| `chore.create` | 新建家务 |
| `chore.batchCreate` | 从模板库批量创建 |
| `chore.update` | 编辑家务，周期变更时重算 `nextDueAt` |
| `chore.setArchived` | 归档 / 取消归档 |
| `log.complete` | 完成打卡（含补录） |
| `log.undo` | 撤销最近一次完成 |
| `log.skip` | 跳过本次 |
| `log.list` | 某家务的历史时间线，分页 |

### 7.2 `reminder` 定时触发器

**触发频率**：每小时整点运行一次（`cron: 0 0 * * * * *`）。

单一 cron 而非按提醒时段配多个触发器：函数启动后取当前本地小时，只处理 `settings.reminderHour` 等于该小时的家庭。这样支持家庭自选提醒时段，却只需维护一个触发器。

**执行流程**：

1. 计算当前本地小时与本地日历日 `dateKey`
2. 查出 `settings.reminderHour == 当前小时` 的家庭
3. 对每个家庭，查出 `archived == false` 且 `nextDueAt <= 今天 + reminderLeadDays` 的家务
4. 若命中为空则跳过该家庭
5. 对该家庭每个 `active` 且 `subscribeQuota > 0` 的成员：
   - 查 `reminder_sends` 确认 `(openid, dateKey)` 不存在，存在则跳过
   - 发送一条汇总订阅消息
   - `subscribeQuota` 减 1，写入 `reminder_sends`

**为什么按家庭聚合成一条推送**：订阅消息每发一条消耗一个额度，而额度只能靠用户逐次点击授权累积。若每件家务单独发一条，五件家务一天烧掉五个额度，两天就断供。汇总成一条（形如「您有 3 项家务待完成，最紧急：刷马桶已逾期 2 天」）能让攒到的额度撑一两个月。

**发送失败处理**：微信返回额度不足等错误时，不扣减本地额度、不写去重记录，把本地 `subscribeQuota` 校正为 0，并记录日志。用户下次进入小程序会看到额度耗尽提示。

## 8. 页面与交互

三个底部 tab，详情与编辑为二级页。

### 8.1 待办（首屏）

这是 90% 的使用场景。进入即是按紧急度四档分组的卡片流，每张卡片显示家务名、图标、到期状态文案（「已逾期 2 天」/「今天到期」/「还有 3 天」）、预估耗时，右侧一个大号完成按钮，点击即记录并自动算出下次到期，并弹出可撤销的轻提示。顶部显示家庭名与成员头像。

「正常」档默认折叠，避免长清单淹没真正紧急的事。

清单为空时（新用户）展示模板库引导入口。

### 8.2 家务

全量管理页。按房间分组展示，支持搜索与筛选归档项。右下角悬浮新建按钮。点击进入详情。

### 8.3 家务详情

显示下次到期与紧急度、周期配置、SOP 备忘、预估耗时、历史时间线（时间 + 完成人 + 备注，分页加载）。操作区提供完成、补录、跳过本次、编辑、归档。

### 8.4 新建 / 编辑家务

表单：名称、图标、房间、周期类型与参数、预估耗时、提前提醒天数、SOP 备忘、上次完成日（仅新建时可填）。

新建页顶部提供「从模板库选择」入口。

### 8.5 我的

家庭名称与成员列表、邀请成员（生成分享卡片、重新生成邀请码）、剩余推送额度与续订按钮、提醒时段设置、加入他人家庭入口。

额度低于 3 条时在此页与待办页顶部显示续订提示。

### 8.6 加入家庭页

通过分享卡片进入时的落地页。显示家庭名与邀请人，确认后加入。

## 9. 模板库

内置 30+ 条常见家务，作为前端本地静态 JSON（`miniprogram/data/chore-templates.js`），不占数据库、不需联网。

每条模板包含：名称、图标、房间、周期类型与参数、预估耗时、SOP 备忘。

必须覆盖用户明确提到的：洗衣机自清洁、刷马桶、换床单、洗油烟机、清洗扫地机器人、浇花、擦玻璃。

其余条目按房间铺开覆盖厨房、卫生间、卧室、客厅、阳台、全屋六个分区的常见周期性家务。

**首次使用引导**：新用户创建家庭后进入模板多选页，勾选后可为每条填写「上次是什么时候做的」（可跳过），确认后批量创建。这让存量家务能在几分钟内导入完毕并立刻得到正确的到期日，而不必等一个完整周期。

## 10. 发布流程

按顺序执行，前两步是后续实现的前置依赖：

1. **注册个人主体小程序账号**：微信公众平台注册，需身份证与本人银行卡验证，当天可通过。获得 AppID。
2. **填写服务类目**：类目决定能申请到哪些订阅消息模板，必须先选对类目才能拿到「事项提醒」类模板。
3. **开通云开发环境**：在小程序管理后台开通，创建环境，记录环境 ID。
4. **申请订阅消息模板**：从模板库选择事项提醒类模板，获得模板 ID 与真实字段名。
5. **配置定时触发器**：随 `reminder` 云函数的 `config.json` 一并部署。
6. **上传代码并提交审核**：个人主体审核通常 1–3 天。
7. **发布**。

### 订阅消息模板字段的处理

订阅消息的模板字段名（`thing1` / `date2` / `phrase3` 等编号与类型）由微信后台实际下发的模板决定，无法预先确定。

应对方式：把消息组装逻辑隔离在单一文件 `cloudfunctions/reminder/lib/message.js` 中，该文件负责把「家务列表」转换为模板所需的 `data` 结构。实现阶段第 0 步是完成上述第 1、2、4 步拿到真实模板，之后只需改这一个文件。在模板落地之前，该文件返回的结构以占位字段名开发，并由单元测试锁定其输入输出契约。

## 11. 测试策略

| 对象 | 方式 |
|---|---|
| 周期计算（`shared/schedule.js`） | Jest 单元测试，覆盖浮动/固定两种类型、跨月、闰年、月末溢出（31 号遇 2 月）、`weekly` 多选、固定周期跳过一次不累积 |

云函数无法跨目录引用代码，小程序也只能引用 `miniprogram/` 根目录内的文件。因此 `shared/` 是唯一真源，由 `scripts/sync-shared.js` 拷贝到消费方目录：

| 消费方 | 目标目录 | 同步的文件 |
|---|---|---|
| `api` 云函数 | `cloudfunctions/api/lib/` | `date.js`、`schedule.js`、`urgency.js` |
| `reminder` 云函数 | `cloudfunctions/reminder/lib/` | `date.js`、`schedule.js`、`urgency.js` |
| 小程序 | `miniprogram/utils/shared/` | `date.js`、`urgency.js` |

这些生成目录不手工编辑，但需随代码提交到仓库——云函数上传时要求依赖文件已在位。

注意小程序**不同步 `schedule.js`**：`nextDueAt` 由云函数计算并持久化，前端只读取该字符串，用 `urgency.js` 做紧急度分档与排序。周期规则因此只有云函数一处在执行，不存在前后端算法漂移的可能；而紧急度只是对已有 `nextDueAt` 与今天做比较，前端本地计算才能保证跨零点时显示正确。

## 13. 后续路线图

第一期上线运行一段时间后再决定是否推进，届时各自重新走设计流程：

- **第二期（协作与洞察）**：负责人与自动轮值、贡献榜与统计看板、微信分享催办、智能周期建议（根据实际完成间隔建议调整周期，避免清单长期全红）、「15 分钟能干啥」推荐
- **第三期（进阶）**：耗材库存管理、拍照记录。两者都需引入云存储与更复杂的数据模型

现有数据模型对二期的预留：`chore_logs` 完整保留了每次完成的时间与完成人，是贡献榜与智能周期建议的数据基础，二期无需数据迁移。
